# Соглашения Raidline

Обязательны для человека, Claude и Codex. Ревьюер проверяет их в первую очередь.

---

| Что | Язык |
|---|---|

## 2. Стиль C#

- Unity 6 → C# 9. Не используем фичи новее (record struct, file-scoped namespace и т.п.), чтобы Core собирался и в Unity, и в `dotnet`.
- Namespace совпадает со сборкой и папкой: `Raidline.Core.Inventory`, `Raidline.Gameplay.Weapons`.
- Один публичный тип на файл, имя файла = имя типа.
- Именование: `PascalCase` — типы, методы, свойства, события, константы; `_camelCase` — приватные поля; `camelCase` — локальные переменные и параметры; интерфейсы начинаются с `I`.
- Сериализуемые поля: `[SerializeField] private float _speed;` — публичные поля запрещены. Для чтения снаружи используем свойство.
- `readonly struct` для маленьких неизменяемых значений (`EntityId`, `ItemUid`, `DamageInfo`); `in` для передачи больших структур.
- Никаких `async void`. Асинхронность — `Awaitable` (Unity 6) в Gameplay и UI; в Core асинхронности нет.
- Исключения только для программных ошибок. Ожидаемые неудачи (не влезает в сетку, нет патронов) возвращаются как `Result` или код ошибки.
- Публичное API Core документируется XML-комментариями (`/// <summary>`).
- Логи — только через `Log` (Infrastructure) с категориями. `Debug.Log` напрямую не вызываем. Отладочные логи вырезаются из релиза через `[Conditional("RAIDLINE_DEV")]`.
- Форматирование задаётся `.editorconfig` в корне.

## 3. Правила Unity для агентов

Агенты не видят редактор, поэтому эти правила защищают проект от поломки.

### .meta-файлы
- **Никогда** не удалять и не пересоздавать существующий `.meta`: от него зависит GUID, а на GUID ссылаются сцены и префабы.
- При переносе или переименовании файла переносится и его `.meta` (`git mv` для обоих).
- Новый файл можно создавать без `.meta`: Unity сгенерирует его при импорте, а человек закоммитит.

### Сцены, префабы, ассеты (YAML)
- Вручную `*.unity`, `*.prefab`, `*.asset`, `*.mat`, `*.controller` **не правим**. Исключение — тривиальное изменение одного значения, явно описанное в задаче.
- Если нужен новый префаб, сцена или ассет, агент пишет **редакторный скрипт** (`Raidline.Editor`, меню `Raidline/…`), который создаёт его детерминированно. Человек запускает его и коммитит результат.
- Текстовые форматы (`.asmdef`, `.inputactions`, `.uxml`, `.uss`, `.json`, `.cs`) агенты правят свободно.

### Проект и пакеты
- `ProjectSettings/` и `Packages/manifest.json` меняет человек или агент по прямому указанию в задаче. Версии пакетов **не угадываем**: берём те, что предлагает Package Manager установленной версии редактора.
- Новые пакеты и сторонние библиотеки добавляются только через решение в `DECISIONS.md`.
- Asset Serialization Mode — **Force Text** (по умолчанию). Не менять.

### Когда Unity открыт
- Пока проект открыт в редакторе, batchmode-тесты на той же папке не запустятся (Unity блокирует проект). Агенты работают в своём git worktree (`AGENTS.md` §4).

## 4. Производительность (горячие пути)

Горячие пути: всё, что вызывается из тика, `Update`/`LateUpdate`, баллистика, ИИ, обновление HUD.

Запрещено в горячих путях:
- `new` для классов, массивов и списков; упаковка (boxing); замыкания в лямбдах; LINQ;
- конкатенация строк, `string.Format`, интерполяция (кроме dev-логов под `Conditional`);
- `GetComponent*`, `Find*`, `Camera.main`, `FindObjectOfType`;
- `foreach` по интерфейсу (`IEnumerable<T>`), который аллоцирует энумератор;
- `UnityEngine.Random` в геймплее (используем `Rng` из контекста);
- `SendMessage`, `Invoke`, корутины для геймплейной логики.

Обязательно:
- пулы (`ObjectPool<T>`, собственные пулы индексов);
- кеширование компонентов в `Awake` или `Init`;
- `NonAlloc`-версии физических запросов или `RaycastCommand`;
- `ProfilerMarker` на каждую систему тика;
- проверка в Profiler: **0 B GC Alloc** в кадре боя. Для задач с пометкой «perf» прикладываем скриншот или цифры в HANDOFF.

## 5. Тесты

- **Core:** каждое правило покрыто EditMode-тестами в `Assets/_Project/Tests/Core/`. Тесты используют только NUnit (`[Test]`, `[TestCase]`, `Assert.That`) без `UnityEngine`. Тогда их можно запустить и в Unity, и через `tools/test-core.sh`.
- **Gameplay/Infrastructure:** EditMode-тесты там, где это возможно без сцены; PlayMode — для интеграции (стрельба по мишени, движение по склону).
- Имя теста: `Method_Condition_Expected`, например `Place_OverlappingItem_ReturnsCollision`.
- Найден баг — сначала пишем падающий тест, потом исправляем.
- Табличные случаи (пробитие, урон) оформляем через `[TestCase]`.
- Красные тесты в `main` недопустимы.

## 6. Git

- Основная ветка — `main`. В неё мержит только человек.
- Ветка задачи: `<агент>/T-XXX-short-name`, например `codex/T-401-item-model`, `claude/T-202-ballistics`. Человек использует `human/…`.
- Коммиты маленькие и логичные: `T-401: add ItemInstance stacking rules`. Баги — `BUG-012: fix …`.
- Перед ревью ветка ребейзится на свежий `main`. **Force-push только в свою ветку задачи**, в `main` — никогда.
- Не коммитим: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, сборки, сгенерированные `*.csproj`/`*.sln` в корне (см. `.gitignore`).
- Бинарные ассеты хранятся через Git LFS (см. `.gitattributes`). Перед первым коммитом выполняем `git lfs install`.

## 7. Ассеты

### Именование

| Тип | Префикс | Пример |
|---|---|---|
| Статический меш | `SM_` | `SM_Crate_Wood_A` |
| Скелетный меш | `SK_` | `SK_Bot_Scav_Base` |
| Префаб | `PF_` | `PF_Weapon_AR_K4` |
| Материал | `M_` | `M_Palette_Main` |
| Текстура | `T_` | `T_Palette_Main` |
| Анимация / контроллер | `A_` / `AC_` | `A_FP_AR_Reload`, `AC_Bot` |
| Звук | `SFX_` | `SFX_Shot_556_Close` |
| Эффект | `VFX_` | `VFX_Impact_Concrete` |
| ScriptableObject-определение | по ID | `ammo.556.fmj.asset` |
| UXML / USS | `UI_` | `UI_Inventory.uxml` |

### Импорт моделей (Blender → Unity)
- Масштаб 1 единица = 1 метр. Экспорт FBX с `Apply Transform`; ось «вперёд» — −Z, «вверх» — Y.
- Материалы при импорте не создаются: назначаем `M_Palette_Main` или нужный общий материал.
- UV — на палитру: каждый цвет — маленький квадрат в `T_Palette_Main`.
- `Read/Write` выключен, Mesh Compression — Medium, генерация лайтмап-UV только для статики, которая получает запечённый свет.
- Правила импорта навязывает `AssetPostprocessor` (T-804), бюджеты треугольников проверяет валидатор (PLAN §3).

### Сторонние ассеты
- Кладём в `Assets/ThirdParty/<Vendor>/<Pack>/` и не модифицируем на месте: копия переносится в `_Project`.
- Каждый пакет записываем в `docs/THIRD_PARTY.md`: источник, лицензия, можно ли использовать коммерчески.

## 8. Данные и ID

- ID определения: `category.group.name`, нижний регистр, только `[a-z0-9_.]`. Пример: `weapon.ar.k4`, `ammo.762.ap`.
- ID **никогда не меняются** после первого коммита, потому что на них ссылаются сохранения.
- Все балансные числа хранятся в SO-конфигах (`HealthConfig`, `BallisticsConfig`, `MovementConfig`, `AIConfig`, `EconomyConfig`), а не в коде.

## 9. Оригинальность и права

- Механики жанра используем свободно. **Не используем** названия, карты, логотипы, модели, звуки, тексты, иконки и узнаваемый UI-стиль Escape from Tarkov / Battlestate Games.
- Оружие называем вымышленно (`K4`, `Skif-9` и т.п.); калибры — реальные (это общеупотребимые обозначения).
- Фракции, торговцы, локации, валюта — свои.
- Ассет без записанной лицензии в репозиторий не попадает.

## 10. Сеть (Fish-Net)

- **Слои.** `Raidline.Core`, `Raidline.Infrastructure`, `Raidline.Data` не ссылаются на Fish-Net. Сетевой код — в Gameplay (`Gameplay/Networking` и сетевые компоненты систем), AI, Presentation, UI, App.
- **Тонкий сетевой слой.** NetworkBehaviour принимает сетевой вызов, переводит его в вызов Core или Gameplay-системы и рассылает результат. Правила игры в NetworkBehaviour не пишем.
- **Именование RPC:** `[ServerRpc]` — префикс `Server` (`ServerMoveItem`), `[ObserversRpc]` — `Observers` (`ObserversShotFired`), `[TargetRpc]` — `Target` (`TargetInventoryResult`).
- **Предсказание.** Replicate-данные (`IReplicateData`) и Reconcile-данные (`IReconcileData`) — маленькие структуры без ссылок. Replicate-метод детерминирован, без `Random`, без чтения `Time.deltaTime` (только `TimeManager.TickDelta`), без звука, эффектов и событий UI при повторе (`IsReplaying`).
- **Проверка на сервере.** Каждый `ServerRpc` проверяет, что вызывающий — владелец объекта, а параметры допустимы (расстояние до предмета, наличие предмета). Клиенту не доверяем.
- **Трафик.** Не рассылаем каждый тик то, что можно вычислить на клиенте. SyncVar и SyncType — для редко меняющегося состояния, частые события — RPC с компактными структурами.
- **Не в Update.** Сетевую логику не пишем в `Update`; используем тик (`TimeManager.OnTick` через `TickRunner`).
- **Версия.** Fish-Net закреплён тегом (сейчас 4.7.3). Обновление — только отдельной задачей с прогоном тестов и записью в DECISIONS.
