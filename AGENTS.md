# AGENTS.md — протокол работы для ИИ-агентов

Этот файл автоматически читает **Codex**; **Claude** читает его через `CLAUDE.md`. Он одинаково обязателен для обоих.

## 0. Проект в двух словах

**Raidline** (рабочее название) — хардкорный экстракшн-шутер от первого лица в духе Escape from Tarkov, но в low-poly стиле, со своим сеттингом и с упором на производительность.
- Unity 6.6 (6000.6.7f1), URP 17.6 (Forward+), C# 9.
- Платформы: Windows и macOS (Apple Silicon). Управление — клавиатура и мышь. Steam Deck, Linux-клиент и геймпад вне рамок (D-014).
- PvE с ботами. Сеть на **Fish-Net 4.7.3 с первого дня**: сервер авторитетен, одиночная игра — режим хоста (D-017). Документация Fish-Net: https://fish-networking.gitbook.io/docs/
- Команда: один человек и два агента — `claude` и `codex`. Мержит в `main` только человек.

## 1. Прочитай перед любой задачей

1. `docs/PLAN.md` — цели, рамки, бюджеты, вехи.
2. `docs/ARCHITECTURE.md` — слои, сборки, тик, команды, системы.
3. `docs/CONVENTIONS.md` — правила кода, Unity, git, ассетов (§3 и §4 особенно важны).
4. `docs/TASKS.md` — твоя задача: карточка и строка в доске.
5. `docs/DECISIONS.md` — принятые решения. Им не противоречь.
6. Последние 5–10 записей в `docs/HANDOFF.md` — что делали до тебя и какие есть открытые вопросы.

## 2. Цикл задачи

1. **Выбор.** Бери задачу из `docs/TASKS.md`, где `Владелец` = твоё имя (`codex` или `claude`), `Статус` = `todo`, а все задачи из «Зависит от» уже `done`. Задачи другого агента и `human` не бери. Если подходящих задач нет, напиши об этом в HANDOFF и остановись.
2. **Проверка соседа.** Выполни `git branch --list 'claude/*' 'codex/*'` и посмотри, какие задачи сейчас в работе у другого агента. Не трогай их модули (колонка «Модуль»).
3. **Старт.** Создай ветку `<имя>/T-XXX-short-name` от свежего `main` и поставь в доске статус `in_progress`.
4. **Работа.** Меняй только то, что относится к задаче и её модулю. Если без изменения чужого модуля не обойтись, сделай минимальное изменение и явно опиши его в HANDOFF.
5. **Проверка.** Запусти `tools/test-core.sh` (если трогал Core) и `tools/test-unity.sh editmode` (если трогал Unity-код и редактор с проектом сейчас не открыт в твоём worktree). Новая логика — новые тесты.
6. **Коммиты.** Маленькие, с ID задачи: `T-XXX: <что сделано>` (на английском).
7. **Сдача.** Сделай rebase на свежий `main` (конфликты в `docs/TASKS.md` разрешай, сохраняя изменения обеих сторон). Поставь статус `review` и добавь запись в `docs/HANDOFF.md` по шаблону.
8. **Ревью** делает другой агент (§6). Если просят исправить, статус становится `changes`, ты исправляешь и снова ставишь `review`. После мержа человек ставит `done`.

Статусы: `todo` → `in_progress` → `review` ⇄ `changes` → `done`; `blocked` — если не можешь продолжать (причину пиши в HANDOFF).

## 3. Жёсткие правила (кратко, полностью — в CONVENTIONS)

- `Raidline.Core` не ссылается на `UnityEngine`. Никогда.
- Геймплейная логика живёт только в `ITickable.Tick` — не в `Update`, `LateUpdate` или `FixedUpdate`.
- Состояние меняется только через команды или `CharacterInputFrame`; UI модель напрямую не трогает.
- Сервер авторитетен: урон, инвентарь, лут, боты, рейд меняются только на сервере. Клиент шлёт ввод (Replicate) и команды (ServerRpc). Core, Infrastructure и Data на Fish-Net не ссылаются (CONVENTIONS §10).
- В геймплее используем `Rng` из контекста, а не `UnityEngine.Random`. Не используем статические синглтоны с изменяемым состоянием, `Find*`, `Camera.main` и `GetComponent` в горячих путях.
- В горячих путях 0 аллокаций: никаких LINQ, замыканий, конкатенации строк и boxing.
- Существующие `.meta` не удаляем и не пересоздаём; при переносе файла переносим и `.meta`.
- `*.unity`, `*.prefab`, `*.asset`, `*.mat` руками не правим: пишем редакторный скрипт (`Raidline/…` в меню), который создаёт или меняет ассет. Человек запускает его и коммитит.
- `ProjectSettings/` и `Packages/manifest.json` меняем только по прямому указанию в задаче. Версии пакетов не угадываем.
- Новые сторонние библиотеки и пакеты добавляем только через решение в `DECISIONS.md`.
- Ничего не копируем из Escape from Tarkov: названия, карты, модели, звуки, UI. Механики использовать можно.
- В `main` не коммитим и не пушим. Force-push разрешён только в собственную ветку задачи.

## 4. Окружение

- Разработка идёт на MacBook (Apple Silicon). Unity Hub ставит редактор в `/Applications/Unity/Hub/Editor/<версия>/`.
- Есть отдельный **Windows-ПК**: на нём собираются релизные Windows IL2CPP-сборки и снимаются замеры производительности (T-903). Синхронизация идёт через удалённый git-репозиторий. Скрипты в `tools/` должны работать и на macOS, и в Git Bash на Windows.
- **Worktree:** каждый агент работает в своей копии рядом с основной, а человек держит Unity открытым в основной.
  - `.worktrees/claude` — Claude
  - `.worktrees/codex` — Codex
  - Папка `.worktrees/` лежит в корне проекта и игнорируется git. Unity её не импортирует: он смотрит только в `Assets/` и `Packages/` своего корня.
  - Создать worktree: `git worktree add .worktrees/<имя> -b <имя>/T-XXX-short-name main` (или `--detach`, если ветки ещё нет).
  - Первый запуск `tools/test-unity.sh` в новом worktree долгий: Unity импортирует проект в его `Library/`.
- **Команды:**
  - `tools/test-core.sh` — быстрые тесты Core через `dotnet test`, без Unity, несколько секунд;
  - `tools/test-unity.sh editmode|playmode` — тесты Unity в batchmode (проект в этом worktree должен быть закрыт в редакторе);
  - `tools/build.sh <win|mac> [dev|release]` — сборки (появится в T-904).
- Если команда недоступна (нет Unity или dotnet в твоей среде), не выдумывай результат. Напиши в HANDOFF «не запускалось: <что>», и ревьюер или человек прогонит это сам.

## 5. Определение готовности (DoD)

Задачу можно ставить в `review`, только если:
- [ ] выполнены все пункты «Готово, когда» из карточки;
- [ ] код компилируется без ошибок и **новых** предупреждений (или в HANDOFF честно написано, что компиляция в Unity не проверялась);
- [ ] для новой логики есть тесты, все тесты зелёные;
- [ ] соблюдены CONVENTIONS §3 (Unity) и §4 (горячие пути);
- [ ] если менялась архитектура, обновлён `docs/ARCHITECTURE.md`; если принято решение, добавлена запись в `docs/DECISIONS.md`;
- [ ] в доске стоит статус `review`, в HANDOFF есть запись.

## 6. Ревью чужой задачи

Ревью задач `codex` делает `claude`, а задач `claude` — `codex`. Порядок:
1. Прочитай карточку и HANDOFF-запись, затем diff (`git diff main...<ветка>`).
2. Прогони тесты.
3. Проверь: соответствие карточке, слои и зависимости сборок, горячие пути, тесты на граничные случаи, `.meta`/YAML, читаемость.
4. Запиши итог в HANDOFF: `APPROVE` или `CHANGES` со списком конкретных замечаний (файл:строка → что не так → как исправить).
5. Сам в чужой ветке не исправляй, кроме опечаток в документации.

## 7. Если что-то неясно

- Не придумывай требования. Если допущение дёшево откатить, прими разумное, явно запиши его в HANDOFF («Допущение: …») и продолжай.
- Если допущение дорогое (архитектура, формат сохранений, новые зависимости), поставь `blocked` и запиши вопрос в HANDOFF в раздел «Вопросы к человеку».
- Нашёл баг вне своей задачи — заведи `BUG-xxx` в `docs/TASKS.md` (владелец `human` назначит) и не чини его молча.

## 8. Шаблон записи в HANDOFF.md

```
## YYYY-MM-DD · <claude|codex> · T-XXX · <review|blocked|APPROVE|CHANGES>
**Сделано:** что именно, ключевые классы и файлы.
**Как проверить:** команды, сцена, шаги в редакторе.
**Не проверено / ограничения:** честно.
**Допущения:** …
**Вопросы к человеку:** … (или «нет»)
**Затронуто вне модуля:** … (или «нет»)
```
